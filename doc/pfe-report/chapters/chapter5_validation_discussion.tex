\chapter[Validation]{Testing, validation and discussion}
\label{ch:validation}

This chapter evaluates whether the implementation described in
Chapter~\ref{ch:implementation} satisfies the functional, non-functional, and KPI
targets defined in Chapter~\ref{ch:requirements} (Table~\ref{tab:kpis}). Validation
combines automated API tests, RAG evaluation harness runs, and manual browser
scenarios. The level of confidence attached to each result class is discussed in
Section~\ref{sec:critical-discussion}.

\section{Validation plan}

Validation was structured at four complementary levels. Pure helper functions
were checked with unit tests. The API was exercised end-to-end through
integration tests against a live PostgreSQL and Redis stack. Browser scenarios
on the Next.js client covered flows that are difficult to assert purely at the
HTTP layer. Finally, a dedicated RAG evaluation harness measured retrieval and
answer quality with automated judge metrics where an API key was available.

Relative to the solutions surveyed in Chapter~\ref{ch:state-of-the-art}, this
project validates capabilities that generic document stores or chatbots typically
lack: \textbf{department-scoped hybrid retrieval}, \textbf{cited streaming answers},
\textbf{per-user feature restrictions}, and \textbf{administrative audit trails}.
Unit coverage is intentionally narrow; the primary automated quality gate is the
\textbf{74-test integration suite}, supplemented by manual UX checks for
security and restriction flows.

\subsection{RAG evaluation results}

Quick evaluation without a configured Gemini API key classified all optimizer
topics as \texttt{general}, yielding \textbf{15/34 PASS} on topic-label
cases---an expected degradation when the LLM optimizer cannot run. With API
credentials, the full harness produces JSON reports under
\texttt{apps/api/eval-reports/} for faithfulness and citation metrics.

\textbf{Interpretation.} Retrieval and serving paths are testable without the
external API, but semantic query optimisation and judged answer quality require it.
The 15/34 result should be read as a \textbf{minimum regression gate}, not as a
measure of answer quality in production. Figure~\ref{fig:ui-val-rag-eval} captures
the quick-mode harness output on 7 July 2026.

\uiscreenshot{ui-val-rag-eval.png}{RAG quick evaluation output showing 15 of 34 topic cases passed without Gemini API key}{RAG quick eval run}{fig:ui-val-rag-eval}

\section{Critical discussion}
\label{sec:critical-discussion}

\subsection{Strengths}

The platform demonstrates end-to-end engineering coherence: traceable requirements,
modular architecture, broad automated test coverage (74/74), and a documented RAG
pipeline that goes beyond a minimal chat demo (hybrid retrieval, reranking, SSE,
feedback, evaluation harness). Manual UX validation confirms that security and
restriction flows are understandable to end users, not only correct at the API layer.

\subsection{Deviations from targets}

\begin{itemize}[leftmargin=*,itemsep=0.2em]
  \item \textbf{RAG judge KPI} --- full faithfulness/relevance run pending; marked \textbf{Partial} in Table~\ref{tab:kpi-results};
  \item \textbf{Scale testing} --- no formal load test for concurrent Ask streams was executed; throughput remains unvalidated;
  \item \textbf{RAG topic eval} --- 15/34 meets the degraded threshold but does not demonstrate production-grade query optimisation without API credentials.
\end{itemize}

\subsection{Limitations}

\begin{itemize}[leftmargin=*,itemsep=0.2em]
  \item \textbf{External LLM dependency} --- latency, cost, and availability depend on Google Gemini;
  \item \textbf{Storage} --- default local disk is not cloud-native object storage;
  \item \textbf{RAG metrics} --- automated judge is itself an LLM; human evaluation remains valuable;
  \item \textbf{Corpus dependency} --- answer quality rises with ingest completeness and chunking quality.
\end{itemize}

\subsection{Threats to validity and confidence level}

Integration tests use a seeded database smaller than production corpora; RAG eval
cases are code-defined and may not cover all host-company domains; manual UX tests
were run on a developer workstation.

\textbf{Confidence assessment:}
\begin{itemize}[leftmargin=*,itemsep=0.2em]
  \item \textbf{High} --- API contracts, RBAC, document access, and notification lifecycles (74/74 integration tests);
  \item \textbf{Medium} --- RAG answer quality and citation faithfulness (eval harness partial without full judge run);
  \item \textbf{Low} --- concurrent load, production-scale corpus behaviour, and long-term operational monitoring.
\end{itemize}

\subsection{Perspectives}

Future work includes SSO/LDAP integration, S3-compatible storage, on-prem embedding
models, horizontal worker scaling, multilingual UI, CI-integrated RAG regression
when API keys are available, and field deployment with user acceptance testing on
real organisational corpora.

\section{Chapter Conclusion}

This chapter validated the Knowledge Platform against the KPIs and sprint domains
defined in Chapter~\ref{ch:requirements}. Automated integration tests passed
without failure (74/74), ingest reliability exceeded the 95\% target on the seeded
corpus, and five manual UX scenarios passed with screenshot evidence.
The RAG judge KPI remains partial pending a full evaluation run with API credentials,
and scale testing was not performed. Critical discussion identified high confidence
in API-level correctness, medium confidence in RAG quality metrics, and acknowledged
limitations related to external LLM dependency and test corpus size. The general
conclusion synthesises these outcomes relative to the objectives stated in the
introduction.
