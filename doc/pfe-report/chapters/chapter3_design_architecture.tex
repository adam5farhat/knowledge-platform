\section{Overall Solution Architecture}
\label{sec:overall-architecture}

The proposed Knowledge Platform adopts a three-tier logical architecture composed of a presentation layer, an application layer, and a data and artificial intelligence layer. This architectural approach promotes separation of concerns by isolating the user interface, business logic, and persistence mechanisms into independent yet collaborative components. Such an organization improves maintainability, scalability, security, and facilitates the future evolution of the platform. Figure~\ref{fig:overall-architecture} presents the overall architecture and the interactions between the main system components.

At the presentation layer, users interact with the platform through a responsive web application that provides access to document management, semantic search, conversational AI, notifications, and administrative functionalities. Authentication relies on a secure session management strategy based on short-lived access tokens stored in memory and refresh tokens maintained as HttpOnly cookies, reducing the exposure of sensitive authentication credentials.

The application layer is implemented as a RESTful API responsible for coordinating all business operations. It exposes dedicated services for authentication, document management, semantic search, conversational AI, notifications, administration, and manager-specific operations. Beyond processing client requests, this layer enforces authorization policies, validates user permissions, orchestrates document processing workflows, and coordinates interactions with the underlying storage and artificial intelligence services.

The data and AI layer manages document persistence, metadata, vector embeddings, user information, notifications, and conversational history. Following each document upload or version update, an asynchronous ingestion pipeline extracts textual content, partitions it into semantic chunks, generates vector embeddings, and indexes the resulting representations to support efficient retrieval. This background processing is performed independently of user requests, thereby preserving application responsiveness while ensuring that newly uploaded documents become searchable once processing is complete.

Together, these three layers establish a modular and extensible architecture capable of supporting enterprise-scale document management and Retrieval-Augmented Generation (RAG), while maintaining a clear separation between presentation, application logic, and data processing responsibilities.

\section{Domain Data Model}
\label{sec:domain-model}

The persisted domain model centres on users and organisational departments,
documents and their versioned content, searchable text chunks with
768-dimensional vector embeddings, conversational threads with answer feedback,
and notification records. Users may hold explicit access to several departments,
which supports both role-based governance and department-scoped document
visibility. Figure~\ref{fig:class-diagram} presents the principal persisted
entities and their relationships across all sprints; sprint-scoped excerpts

\textbf{PostgreSQL with pgvector vs.\ dedicated vector database:} storing relational
metadata and vector embeddings in the same database simplifies hybrid retrieval,
transactional consistency, and department-scoped filtering within a single query
layer~\cite{pgvector-docs}.

\textbf{Managed Gemini APIs vs.\ self-hosted open-weight models:} hosted embedding
and chat services reduce operational overhead while delivering strong multilingual
representations at the dimensionality required by this deployment~\cite{google-gemini-docs}.

\textbf{In-process background worker vs.\ separate worker service:} running the
ingest consumer alongside the API reduces deployment complexity for a
prototype-scale platform, at the cost of tighter coupling when scaling out
horizontally.

\section{Dynamic Interaction Design by Sprint}
\label{sec:sprint-design}

Sections~\ref{sec:overall-architecture}--\ref{sec:technology-justification} describe
\textbf{what} the platform is made of. This section describes \textbf{how} people,
services, and background processes interact during real use. For each development
sprint in Table~\ref{tab:sprints} of Chapter~\ref{ch:requirements}, the design is
presented in three steps:
\begin{enumerate}[leftmargin=*,itemsep=0.2em]
  \item \textbf{Sprint scope} --- the capabilities delivered in that iteration;
  \item \textbf{Scoped structural views} --- the sprint use-case model and domain class model;
  \item \textbf{Interaction sequence diagrams} --- step-by-step flows between the user interface, application services, background workers, and external systems.
\end{enumerate}
The full diagram catalog is presented in Section~\ref{sec:sprint-design}; implementation
details appear in Chapter~\ref{ch:implementation} and validation in
Chapter~\ref{ch:validation}.

\section{Chapter Conclusion}

This chapter established how the Knowledge Platform is structured and how its
parts interact at design time. The three-tier architecture separates user-facing
workflows from business coordination and from persistence and AI processing,
while subsystem boundaries clarify ownership of authentication, documents,
search, conversations, and governance. Technology choices favour a pragmatic
TypeScript stack that supports streaming answers, hybrid retrieval, and
manageable deployment for a prototype-scale enterprise system. Sprint-scoped
interaction diagrams complete the picture by showing how real user journeys
unfold across the web application, API services, and background workers.
Together, these design artefacts provide an implementable blueprint whose
adequacy is verified in Chapters~\ref{ch:implementation}
and~\ref{ch:validation}.
